# معماری Phase 4 — وضعیت جست‌وجو، هرس و چرخهٔ عمر جدول انتقال

این سند تغییرات ساختاری Phase 4 را توضیح می‌دهد. همهٔ قابلیت‌های جدید گزینهٔ UCI با پیش‌فرض `false` هستند. با خاموش‌بودن همهٔ آن‌ها، امضای جست‌وجو (گره، امتیاز، بهترین حرکت) روی ۲۲ موقعیت `tools/positions-v3.fen` در عمق ۵ با baseline `11bf331` دقیقاً یکسان است (`benchmarks/v4-baseline/classical-depth5.json` در برابر `benchmarks/v4-experiments/depth5-off.json`).

## مالکیت وضعیت

| وضعیت | مالک | طول عمر | پاک‌سازی |
|---|---|---|---|
| `Heuristics` (killer و history) | `IterationState` هر `go` | یک جست‌وجو | خودکار با هر `go`؛ بدون `Persistent History` پیش از هر فراخوانی root |
| `hints` (بهترین حرکت هر hash) | `IterationState` | یک جست‌وجو | خودکار |
| `Table` (TT) | `IterationState`؛ با `Persistent Hash` در `HashSlot` بین `go`ها | یک جست‌وجو، یا تا پاک‌سازی | `ucinewgame`، `Clear Hash`، هر `setoption`، تغییر اندازه |
| `Game.barrier` | `Game` | مسیر جست‌وجو | با `unplay_null` بازگردانده می‌شود |

### Persistent History (`setoption name Persistent History value true`)

- killerها و history بین iterationهای عمیق‌شوندهٔ تدریجی و بین تلاش aspiration و re-search همان عمق حفظ می‌شوند.
- در آغاز هر عمق history نصف می‌شود (aging).
- به‌روزرسانی از نوع gravity است: `h += b - h·|b|/16384` با `b = min(depth², 1600)`؛ مقدار هرگز از بازهٔ ±16384 خارج نمی‌شود (تست `history_gravity_is_bounded`). حرکت‌های آرامی که پیش از حرکت cutoff امتحان شده‌اند جریمهٔ هم‌اندازه می‌گیرند.
- جست‌وجوی قطع‌شده فقط اطلاعات ترتیب حرکت را باقی می‌گذارد؛ نتیجهٔ آن استفاده نمی‌شود.
- `Heuristics` هرگز از یک `go` به بعدی منتقل نمی‌شود؛ بنابراین بازی جدید، موقعیت جدید یا تغییر ارزیاب اطلاعات کهنه به ارث نمی‌برد.
- بدون این گزینه، مسیر به‌روزرسانی Phase 3 (افزایش اشباعی تا ۷۰٬۰۰۰ و بدون جریمه) دقیقاً حفظ شده است.

### LMR (`setoption name LMR value true`)

شرایط کاهش: عمق ≥ ۳، اندیس حرکت ≥ ۳ (یعنی دست‌کم سه حرکت قبلی کامل جست‌وجو شده‌اند)، حرکت آرام (نه capture، نه en passant، نه ترفیع)، گره در کیش نیست، حرکت کیش نمی‌دهد، حرکت hash یا killer نیست. مقدار کاهش:

```text
r = floor(0.5 + ln(depth) · ln(index + 1) / 2.5) − [PV node]
r = clamp(r, 0, depth − 2)
```

بنابراین عمق فرزند همیشه ≥ ۱ است و underflow ممکن نیست (تست `lmr_never_reduces_to_zero_depth` برای همهٔ عمق‌ها و اندیس‌ها). جست‌وجوی کاهش‌یافته zero-window است؛ هر fail-high در عمق کامل (با PVS یا پنجرهٔ کامل) دوباره جست‌وجو می‌شود، پس کاهش هرگز به‌تنهایی alpha را بالا نمی‌برد و PV را نمی‌سازد. در ریشه کاهشی انجام نمی‌شود.

### Null Move (`setoption name Null Move value true`)

شرایط: گره zero-window (غیر PV)، نبود کیش، عمق ≥ ۳، `|beta| < MATE−100`، طرف حرکت دست‌کم یک مهرهٔ غیر از پیاده و شاه دارد، ارزیابی ایستا ≥ beta، و حرکت قبلی null نبوده است. کاهش R برابر ۲ و از عمق ۷ برابر ۳ است. از عمق ۸ نتیجه با جست‌وجوی کاهش‌یافتهٔ همان گره (بدون null) تأیید می‌شود. مقدار برگشتی `beta` است، پس امتیاز مات اثبات‌نشده بازگردانده نمی‌شود.

- `Board::null_move` از crate شطرنج en passant را حذف و نوبت را عوض می‌کند و در کیش `None` می‌دهد.
- `Game::play_null` شمارندهٔ نیم‌حرکت را یک واحد افزایش و `barrier` را روی موقعیت null قرار می‌دهد؛ تکرار فقط از `history[barrier..]` شمرده می‌شود، پس هیچ موقعیت پیش از null در زیرشاخه تکرار حساب نمی‌شود (تست `null_move_is_a_repetition_barrier_and_restores_state`). `unplay_null` هر سه مقدار را بازمی‌گرداند.
- زیرشاخهٔ null فقط در گره‌های با شمارندهٔ صفر TT را می‌خواند/می‌نویسد؛ همان محدودیت قبلی که مستقل از مسیر بودن را تضمین می‌کند.
- در ساخت `nnue-stack` موقعیت null مانند هر موقعیت دیگری push/pop می‌شود؛ آزمون معادل‌سازی stack و cache با هرس فعال گذشت.
- **محدودیت مهم:** بدون PVS تقریباً هیچ گره zero-window وجود ندارد؛ null move فقط با PVS (یا داخل probeهای LMR) فعال می‌شود. در بنچمارک عمق ثابت بدون PVS، تعداد گره‌ها با و بدون null move دقیقاً برابر بود.

### Persistent Hash (`setoption name Persistent Hash value true`)

- جدول از `HashSlot` (درون `Arc<Mutex<…>>`) به رشتهٔ جست‌وجوی تک‌نخی منتقل و پس از پایان برگردانده می‌شود. هر پاک‌سازی `epoch` را افزایش می‌دهد؛ جست‌وجویی که پیش از پاک‌سازی شروع شده جدول کهنه را برنمی‌گرداند.
- `ucinewgame`، `Clear Hash` و **هر** `setoption` (شامل Hash، EvalFile، Positional، NNUE و گزینه‌های هرس) جدول را پاک می‌کند، چون امتیازها به ارزیاب و پیکربندی جست‌وجو وابسته‌اند.
- اگر ظرفیت با `Hash` فعلی برابر نباشد، جدول تازه ساخته می‌شود.
- خروجی `info string tt reused <true|false> hashfull N` استفادهٔ مجدد را گزارش می‌کند.
- جست‌وجوی موازی (`Threads > 1`) همچنان جدول خصوصی هر worker دارد و جدول را نگه نمی‌دارد؛ TT مشترک موازی Milestone جداگانه است و انجام نشده است.

**استدلال صحت:** امتیاز TT فقط در گره‌هایی خوانده یا نوشته می‌شود که شمارندهٔ نیم‌حرکت صفر است (محدودیت Phase 3 دست‌نخورده باقی ماند). در چنین گرهی آخرین حرکت برگشت‌ناپذیر بوده است، پس هیچ موقعیت قبلی از تاریخچه نمی‌تواند در زیرشاخه تکرار شود و شمارندهٔ ۵۰ حرکت صفر است. بنابراین مقدار گره تابع (موقعیت، عمق، ارزیاب، پیکربندی) است و به مسیر یا `go` قبلی وابسته نیست. ارزیاب و پیکربندی با پاک‌سازی روی هر `setoption` ثابت می‌مانند؛ امتیاز مات نسبت به ply نرمال می‌شود؛ کلید ۶۴ بیتی کامل مقایسه می‌شود. حرکت hash فقط برای ترتیب استفاده می‌شود و با حرکت‌های قانونی مقایسه می‌شود.

## چیزهایی که عمداً تغییر نکرده‌اند

- محدودیت استفاده از امتیاز TT به گره‌های با شمارندهٔ صفر.
- ارزیاب پیش‌فرض (فقط ارزش مهره)، PVS و Aspiration (پیش‌فرض خاموش).
- مسیر NNUE و پیش‌فرض‌های آن.
- الگوریتم موازی.
